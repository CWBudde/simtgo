# The tile track

A second code generator, with a different bet from the SIMT track's. The SIMT
track translates a kernel somebody wrote; the tile track **records a graph of
operations and writes the kernel itself**, so the user never spells a thread
index.

CUDA Rust's tile track embeds a kernel AST in the host binary with a proc macro.
Go has no macros, so the graph is instead recorded **at run time**: the Go
program builds it by executing ordinary Go calls, and the code generator sees
the finished graph. The payoff is the same — a chain of operations becomes one
kernel with one pass over memory, instead of one kernel and one temporary buffer
per operation.

```go
g := tile.New(ctx)
out := tile.Hypot(tile.FIR(tile.Scale(g.Input(re), 0.5), h), g.Input(im))
vals, err := out.Materialize()
```

Nothing touches the device until `Materialize`.

## Fusion, and the one operation that cannot fuse

`tile/codegen.go` folds every **elementwise** node into one C expression
evaluated at the thread's index. No node becomes a temporary and no
intermediate buffer is allocated; `Scale`, `Add`, `Mul`, `Hypot`, `Sqrt` and
`Abs` all disappear into the expression.

A **windowed** operation cannot, because it reads a neighbourhood rather than a
point. `FIR` therefore stages a shared tile — _including its halo, computed
through the very same fused expression_ — and leaves its result in a local. That
last clause is the part worth noticing: the halo is not a second code path. The
elements outside the block's own range go through the identical fused
expression, evaluated at a shifted index, so there is exactly one definition of
what each input element is worth.

```cuda
// generated by github.com/CWBudde/gocuda/tile: 6 operations fused into one kernel
extern "C" __global__ void fused(float* __restrict__ out, int out_len, const float* __restrict__ p0, int p0_len, ...)
{
	int base = (int)(blockIdx.x * blockDim.x);
	int t = (int)threadIdx.x;
	int i = base + t;

	int taps3 = p1_len;
	__shared__ float tile3[320];
	for (int k = t; k < (int)blockDim.x + taps3 - 1; k += (int)blockDim.x)
	{
		int src = base + k - (taps3 - 1);
		tile3[k] = (src >= 0 && src < out_len) ? (0.5f * p0[src]) : 0.0f;
	}
	__syncthreads();
	float v3 = 0.0f;
	for (int k = 0; k < taps3; k++)
	{
		v3 += p1[k] * tile3[t + taps3 - 1 - k];
	}

	if (i < out_len)
	{
		out[i] = hypotf(v3, p2[i]);
	}
}
```

`MaxTaps` bounds the halo at 64, because the shared tile needs a compile-time
extent. `BlockSize` is 256 and the tile is `BlockSize + MaxTaps` wide.

## The cost of not fusing is measured, not asserted

`MaterializeStepwise` runs the same graph one kernel per operation. It exists so
that the fusion claim has a control:

|          | kernels |                                                   time |
| -------- | ------: | -----------------------------------------------------: |
| fused    |       1 |                                           14.3–14.9 ms |
| stepwise |       3 | 16.3–20.7 ms (1.15–1.39× slower, plus two temporaries) |

4.19M samples on the T550, `go run -tags cuda ./examples/tilefir`.

The margin is smaller than the number of kernels suggests, and that is honest
rather than disappointing: this pipeline is memory bound either way, so what
fusion saves is the temporaries and the extra passes, not the launches.

## Aliasing: the promise is made, then checked

Inputs are emitted `const float* __restrict__` and the output
`float* __restrict__`, for the same reason the SIMT track emits them. **A
qualifier nothing verifies is undefined behaviour with a comment on it**, so the
order matters: make the promise, then check it.

`checkAliasing` runs in `Tensor.run` — the tile analogue of `Kernel.launch`, and
the point both `Materialize` and `MaterializeStepwise` funnel through, so one
check covers both paths. Only an overlap with the **output** is refused, because
`out` is the only thing a fused kernel writes and `restrict` forbids reaching a
_modified_ object through another pointer. Same position the SIMT check takes.

**Nothing can fail that check today, and saying so is the honest part.** `run`
allocates `out` with `cuda.NewSlice` on every call, so it cannot be a buffer the
graph already holds, and `generate` emits one parameter per distinct node, so
`Mul(t, t)` is one pointer rather than two. The gap is prospective:
device-resident values is what opens it, and the unused `node.dev` field has
been anticipating exactly that.

What _is_ live is the case the check **accepts**. `MaterializeStepwise` caches a
materialised node's buffer, so a node feeding both operands is handed to the
kernel twice and `p0` and `p1` are one allocation. Two readers of one buffer is
what `restrict` allows, so the launch has to go through and compute the right
numbers rather than be refused for looking suspicious. That is the test that
runs on the device; the rest is arithmetic on device addresses and is tested
without one, the same argument `simt/alias_test.go` makes for itself.

[`../SPEC.md`](../SPEC.md) is deliberately silent about all of this: it is the
SIMT subset's contract and mentions the tile track nowhere.

## What the sanitizer sweep covers here

Worth stating because it was nearly missed. The `compute-sanitizer` sweep wraps
`tile`'s tagged test binary alongside `simt`'s and `cuda`'s, so the **fused
kernels this generator writes** are covered. A `simt`-only sweep would have
missed a second code generator entirely. See
[`verification.md`](verification.md#8-compute-sanitizer-four-tools).

## Where it stops

Seven operations — `Scale`, `Add`, `Mul`, `Hypot`, `Sqrt`, `Abs` and the
windowed `FIR` — over 1-D `float32`, fed by `Graph.Input`. No reductions, no 2-D, no broadcasting
or slicing, no graph optimisation, and **chained windowed operations are
rejected by design**: the halo of the outer window would need values the inner
one does not have at those indices.

Phase 6 in [`../PLAN.md`](../PLAN.md) is where that changes, and reductions plus
2-D tiling are a rewrite of this code generator rather than an extension of it.
